| 维度 | 结论 |

## 三、实现方式差异（功能等价，机制不同）

1. **中文搜索**：PRO「自适应数据库分词器」直接改数据库查询；我们维护插件侧索引（约 1.3 万条目，全量重建 ~5s，增量随库更新）。差异：PRO 随 Emby 索引自动生效，我们需要重建任务兜底；搜索排序规则由我们实现。
2. **本地元数据源合成粒度**：官方缓存的 JSON 是「备选语言刮削逻辑处理后的综合结果」；我们按请求落盘（含图片语言改写），并对 provider 实际消费的对象做记录。字段级合并规则可能不完全一致，导致同一 tmdbid 在不同语言请求下的缓存内容与官方略有差异。

---

## 四、Emby 服务端硬限制（插件无法绕过）

| 限制 | 原因 |
|---|---|
| 同目录多版本合并 8 部上限（扫描端） | `Emby.Naming.VideoListResolver` 硬编码；插件只能改任务侧上限 |
| 按库片头时长可视化 | Emby 设置页无对应 UI 插槽 |
| 原生 DV P7 双层信息 | 服务端探测层不暴露 EL 数据，需外部 ffprobe ≥9 |
| 电影片尾无跳过机制 | Emby 客户端未提供电影片尾按钮 |

## 五、部署与回滚

- 插件目录：`<emby配置>/plugins/`，结构 `StrmAssistantLite.dll` + `StrmAssistantLite.deps/` + `zh/` + `zh-hant/`
- 配置文件：`Strm Assistant.json`（与社区版/官方版同名，升级不丢配置）
- 回滚：还原 `StrmAssistantLite.dll.bak-*` 后重启容器
- 生产验收：`health=healthy`、设置页 200、插件列表显示 `Strm 助手`、启动日志无 `Error creating`/`Init Failed`

## 六、rffmpeg sidecar（可选）

见 `docs/rffmpeg-deployment.md`：master 侧 `rffmpeg` + 静态 ssh + sqlite；worker 为独立容器（同路径只读挂载）；只代理 `ffprobe`，不接管转码。单机部署无性能收益，跨机部署受限于「worker 必须能读到同一份媒体」。
